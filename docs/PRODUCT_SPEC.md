# JobPilot 产品规格

> 文档状态：Phase 0 已批准的产品规格基线。  
> 实现状态：本文描述目标与边界，不代表相关功能已经实现。

## 1. 产品定位

JobPilot 是一个面向求职者的跨招聘平台 AI 求职工作台。它把用户在不同招聘网站上主动发现的岗位，汇总到一个个人工作空间中，支持后续的岗位管理、投递跟踪、简历匹配、面试准备、知识沉淀和结果复盘。

JobPilot 不替代招聘网站，也不建设独立的招聘职位数据库。招聘网站继续负责岗位发现、HR 沟通和正式投递；JobPilot 只处理用户主动带入工作台的信息以及用户自行创建的求职资料。

产品的核心价值不是“替用户自动找工作”，而是让分散的求职信息、证据和行动形成一条可追溯的工作流：

岗位捕获 → 岗位理解 → 简历与证据匹配 → 投递跟踪 → 面试准备与复盘 → 结果分析 → 下一轮行动

## 2. 目标用户

### 2.1 核心用户

正在同时使用多个招聘平台、并需要系统管理求职过程的个人求职者，尤其是：

- 同期关注和投递多个岗位的人；
- 针对不同岗位维护多个简历版本的人；
- 希望用 AI 辅助理解 JD、梳理证据和准备面试，但仍要掌握最终判断权的人；
- 希望沉淀真实面试问题和求职结果，用于后续复盘的人。

### 2.2 用户特征与约束

- 用户已在招聘网站中完成登录并主动打开具体岗位页面；
- 用户愿意在保存前检查和确认采集结果；
- 用户的简历、文档、面试记录属于敏感个人数据，需要严格按用户隔离；
- 产品面向个人工作台场景，V1 不包含招聘方、猎头或团队协作角色。

## 3. 核心问题

### 3.1 信息分散

岗位分布在多个网站，字段、链接和页面结构不同。收藏记录容易重复、失效或脱离上下文。

### 3.2 求职行动缺乏统一状态

“收藏、计划投递、已投递、笔试、面试、结果”等状态常散落在网站收藏夹、表格和聊天记录中，难以形成可靠的个人事实来源。

### 3.3 JD、简历与真实证据脱节

普通匹配工具往往只输出一个分数，无法回答具体岗位要求由哪段经历、哪个简历版本、哪项作品或哪次回答支撑。

### 3.4 准备与复盘无法形成闭环

真实面试问题、回答表现和最终结果没有回流到下一轮准备中；用户难以区分客观事实、AI 解释和策略建议。

## 4. 产品原则

### 4.1 用户触发、用户确认

浏览器插件只读取用户当前主动打开的具体岗位页面。标准流程是：

用户点击插件 → 当前页面 DOM 解析 → 展示结构化结果 → 用户确认或修正 → 保存到 JobPilot

采集采用以下三级路径，只有上一级不可用或结果不足时才进入下一级：

1. 自动解析当前岗位页 DOM；
2. 用户手动选择当前页面内容；
3. 用户手动粘贴 JD。

预览、补充和修正是三条路径共有的确认步骤，不构成第四级采集方式。任何采集结果在用户确认前都不得作为正式岗位记录写入系统。

### 4.2 数据库是业务事实来源

岗位、投递、简历版本及其状态以 API 后端和 PostgreSQL 中的定义为准。Web 与插件消费同一套业务 API，不各自发明状态、字段或业务规则。

### 4.3 AI 是受约束的辅助能力

AI 输出必须经过结构化解析和校验，再转换为领域结果。产品需要明确区分：

- 用户或招聘页面提供的原始事实；
- 系统根据事实计算的客观统计；
- LLM 生成的解释、评价和建议。

不得把 LLM 原始响应直接展示为系统事实，也不得把少量个人数据包装成可靠的机器学习推荐结论。

### 4.4 简单架构优先

V1 采用单体 API、PostgreSQL 与 pgvector、S3 兼容对象存储抽象，以及 Web 和 Chrome Extension 两个客户端。只有在真实需求和可验证瓶颈出现后，才考虑进一步拆分。

## 5. 产品边界

### 5.1 JobPilot 负责

- 用户主动触发的当前岗位页面捕获与人工兜底；
- 跨平台岗位的统一保存和管理；
- 投递状态及关键求职事件的记录；
- 多个简历版本的管理及与求职过程的关联；
- 结构化 JD 分析和简历匹配辅助；
- 用户文档的检索增强与来源追溯；
- 面试准备、显式流程驱动的模拟面试和复盘；
- Requirement → Evidence → Resume → Portfolio → Interview 的证据链；
- 基于真实求职记录的客观统计、LLM 辅助解释和策略建议。

### 5.2 招聘平台继续负责

- 岗位发现与搜索排序；
- 招聘平台账号、登录和风控；
- 与 HR 或招聘方沟通；
- 正式投递及平台内流程；
- 招聘方提供的岗位真实性与时效性。

### 5.3 采集合规红线

JobPilot 明确禁止：

- 后台批量爬虫、自动翻页或扫描职位列表；
- 绕过验证码、登录限制或其他访问控制；
- 调用隐藏接口批量采集；
- 高频请求招聘网站服务器；
- 未经用户主动触发读取或保存页面数据；
- 将采集结果汇总为对外提供的岗位数据库。

## 6. 核心产品能力

### 6.1 Cross-platform Job Capture

Chrome Extension 通过统一 JobSiteAdapter 契约识别当前页面、提取岗位并校验结果。BOSS 直聘、牛客、实习僧、猎聘、国聘各自使用独立 Adapter；generic/manual Adapter 提供通用与人工兜底。

不同 Adapter 最终输出统一的 JobCapture，至少表达来源、来源链接、岗位名称、公司、薪资、地点、JD 正文和采集时间。确切字段、必填规则和错误语义以接口及数据模型文档为准。

### 6.2 统一岗位与投递工作台

用户可在一个工作台内查看自己保存的岗位、记录投递进展、关联使用过的简历版本，并保留后续分析所需的时间和来源信息。状态定义由后端统一管理。

### 6.3 结构化 AI 分析

后续阶段通过 JDAnalyzer、ResumeMatcher 和 InterviewEvaluator 等清晰边界提供 AI 能力。每项能力都需要版本化输入、结构化结果、校验、失败处理和必要的来源说明。

### 6.4 求职知识库与 RAG

用户可将授权文档存入个人知识库。文件本体通过 S3 兼容抽象保存，元数据、切分结果和向量索引保存在 PostgreSQL/pgvector。检索结果必须受用户边界约束，并尽可能返回可定位的来源片段。

### 6.5 Evidence Map

Evidence Map 在后期阶段逐步建立以下可追溯关系：

岗位要求 → 相关经历 → 简历证据 → 作品集证据 → 面试问题 → 历史回答表现

V1 的目标是提供可检查的基础证据链和缺口提示，不是建立自动判断候选人价值的黑盒评分系统。

### 6.6 Feedback Loop

JobPilot 将岗位、投递、面试、结果、真实问题和回答表现连接起来，形成复盘材料。早期只提供客观统计、结果分析、LLM 辅助解释和策略建议，不宣称“精准岗位推荐”或因果结论。

## 7. MVP 范围

### 7.1 MVP 目标

MVP 对应 Roadmap 的 Phase 1–4。它只验证一条可运行、可测试的核心垂直闭环：

用户身份与数据隔离 → 主动捕获或手工录入岗位 → 保存到个人岗位库 → 跟踪申请状态 → 关联简历版本

### 7.2 MVP 包含

- 可运行的 Web、Extension、API 和 PostgreSQL 工程基础；
- 基础认证及所有核心资源的用户级隔离；
- 统一 JobCapture 契约、generic/manual 兜底和至少一个作为参考实现的平台 Adapter；
- 当前页面采集、用户确认、岗位保存和基础岗位管理；
- Application 的创建、状态更新和必要的历史可追溯信息；
- ResumeVersion 的基础保存、版本识别及与申请记录的关联；
- 核心单元测试、API 集成测试、基于保存 HTML fixture 的 Adapter 测试，以及主流程浏览器测试。

具体由哪个 V1 平台先作为参考 Adapter，应在 Phase 3 开始前依据页面稳定性、可合法取得的测试 fixture 和验证成本确定。

### 7.3 MVP 明确不包含

- 五个平台 Adapter 全部完成；
- JD AI 分析、简历匹配或自动改写；
- 文档知识库、向量检索或 RAG；
- 面试准备、模拟面试或 Evidence Map；
- 结果推荐模型、岗位推荐或自动投递。

## 8. V1 范围

V1 对应 Roadmap 的 Phase 5–11。在 MVP 闭环稳定后，按顺序增加：

- BOSS 直聘、牛客、实习僧、猎聘、国聘五个平台的独立 Adapter 与人工兜底；
- 结构化 JD 分析和简历匹配；
- 用户文档、pgvector 检索及来源可追溯的 RAG；
- 面试准备和显式 Workflow/State Machine 驱动的模拟面试；
- 基础 Evidence Map 与求职反馈闭环；
- 客观分析、可靠性加固、可观测性和作品集发布材料。

V1 是个人求职工作台的首个完整版本，不承诺覆盖招聘平台的所有页面变体，也不承诺 AI 输出等同于专业招聘意见。

## 9. 非目标

以下内容不属于 MVP 或 V1：

- 自建公开或商业招聘职位库；
- 自动搜索、批量采集、自动投递或自动联系 HR；
- 绕过招聘平台的登录、验证码、访问控制或使用限制；
- 招聘方 ATS、企业招聘后台、团队协作和复杂权限体系；
- 原生 iOS/Android 客户端；
- 基于少量用户数据的“精准推荐”或成功率预测模型；
- 无来源、不可解释的综合匹配分；
- 通用 Agent 平台、复杂多智能体编排或为展示技术而引入 Agent Framework；
- 微服务、Kafka、Kubernetes、Elasticsearch、MongoDB 或独立向量数据库；
- 在没有明确产品价值与维护评估前增加新的核心基础设施。

## 10. 成功标准

### 10.1 MVP 成功标准

- 用户能在明确授权和确认后，将当前岗位页或手工输入保存为自己的岗位记录；
- 用户能管理岗位、记录申请状态并关联一个可识别的简历版本；
- 不同客户端通过同一 API 契约和后端状态定义工作；
- 用户 A 无法读取或修改用户 B 的岗位、申请和简历数据；
- 核心流程有自动化测试，Adapter 测试不依赖实时招聘网站；
- 系统没有实现或暗含后台批量采集、自动投递及其他产品红线能力。

### 10.2 V1 成功标准

- 五个平台 Adapter 在保存的代表性 fixture 上通过契约测试，解析失败时可进入人工兜底；
- AI 分析返回经过校验的结构化结果，错误可恢复，原始模型输出不直接成为领域事实；
- 文档检索严格按用户隔离，并能从回答回溯到来源片段；
- 模拟面试由可检查、可恢复的显式状态流驱动；
- Evidence Map 能展示至少一条从岗位要求到用户证据及面试记录的可追溯链路；
- 分析页面明确区分客观统计与 AI 解释，不宣称精准推荐；
- 关键用户流程通过发布门禁，并具有足以演示架构取舍、测试策略和迭代过程的作品集材料。

## 11. 风险与待决策项

- 招聘网站 DOM 会变化。Adapter 需要 fixture 回归测试、有限人工验证和长期维护策略，不能承诺永久兼容。
- 平台条款和页面访问规则可能变化。每个平台 Adapter 上线前需要重新核对合规边界。
- 简历、面试和求职结果是敏感数据。认证方式、数据保留、删除、日志脱敏和对象存储访问策略必须在相应实现阶段明确。
- LLM 的成本、延迟、可用性和输出漂移需要在 Phase 6 通过提供方抽象、结果版本和评估样例约束。
- MVP 的首个平台 Adapter 尚未指定；该选择不改变统一契约和人工兜底边界。
